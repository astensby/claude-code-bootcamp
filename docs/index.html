What this repository is

This is the repository for the Claude Code for Developers bootcamp. It holds the exercises for the day, a small app to practise on with its data and a backlog of issues, and a toolkit of reference skills, agents, hooks and goals you can copy into your own projects. Every exercise works on your own data or your own repo first; this repo is what you use when you have nothing to bring.

5 exercisesOne day in four blocks, with one demo and one take-home. Stop 2 has the timetable.
8 issuesIn BACKLOG.md, each with an acceptance list. scripts/seed-issues.sh creates them in your repo.
27 testsVitest, under five seconds. Lint reports 37 warnings on purpose; that is issue #7.
5 tagsex2-start to ex5-done: the finished state of every exercise, for when you fall behind.

Set up before the day

One click and five commands. On github.com/astensby/claude-code-bootcamp click Use this template and create <you>/claude-code-bootcamp. Private is fine. Then, with <you> replaced by your GitHub user name:

git clone https://github.com/<you>/claude-code-bootcamp && cd claude-code-bootcamp
git remote add upstream https://github.com/astensby/claude-code-bootcamp && git fetch upstream --tags
gh repo set-default <you>/claude-code-bootcamp
npm ci
scripts/preflight.sh

The copy button chains the five commands with &&, so a failed clone stops the rest. Replace <you> before you press Enter.

  • Why the upstream remote: templates copy files only. The tags and the solutions branch come from upstream, which is public.
  • Why set-default: otherwise gh picks upstream, and your issues and PRs would land in the template repo.
  • Preflight prints one green/red table: Node 22 or newer, npm, git, Claude Code and its login, gh and its login, gh pointing at your own repo, the install and the tests. Fix anything red before the day; if you are attending the bootcamp, reply to the invitation email with the output and we help.

On the day

Before E2a, run scripts/seed-issues.sh. It creates the eight issues from BACKLOG.md in your repo, plus eight labels: ex2 to ex5 for the exercises and ready, needs-spec, loop-review for the loop. Templates do not copy issues. The script refuses to seed the template itself, and stops when gh cannot tell which repo is yours.

Known bugs

The app ships with three known bugs, listed as issues in the backlog: a bad URL is accepted (#5), lint debt (#7), and a README that documents a flag that does not exist (#8).

E1 · Data to interactive dashboard

block 1 · 15 min · exercises/01-dashboard.md

In this exercise we will take a dataset, find out what is in it, and build a single-file interactive HTML dashboard from it. Your own CSV, JSON or export first; the repo's data/ if you have nothing to bring, or data/alt/ for public data. Keep the linkr data if you want to serve the dashboard from the app later (issue #6).

  1. Analyse @data/, or a file of your own, and explain what is in it
  2. Show me the most interesting findings
  3. Build an interactive HTML dashboard from it
    Build a single-file interactive HTML dashboard at dashboard/index.html from @data/ that answers: which links get the most clicks, how traffic moves over the week, which referrers matter. List your assumptions at the end.
  4. Open it. How can we make it better?
Done whenThe dashboard opens in a browser and one change you asked for is in.
Stretch, Compound, Stuck?
  • Ask it to open the page itself (with the Chrome extension or the desktop app's browser) and fix what it sees.
  • Ask "what did you assume about the data?" and check the answer against data/clicks.csv.
  • Copy toolkit/skills/dataset-profile/ into .claude/skills/ and run /dataset-profile data/.

Compound: what did you only notice once the page was open? Nobody checked it before you did; block 3 is where that changes.

E2a · Plan and brainstorm

block 2 · 15 min · exercises/02a-plan-brainstorm.md

In this exercise we will turn an idea into a spec before any code is written: an interview, three options as a page you can click through, then SPEC.md. A feature your dashboard does not have yet, or issue #1 (links can expire) if you want an open question the interview should find. Step 3 is the one to pay attention to: the same move reviews a PR in E4.

  1. Pick a feature for your dashboard, or issue #1 in the repo
  2. "Interview me about it, one question at a time"

  3. "Show me three ways to build it, as one HTML page I can click through." Open it, pick one, say why

E2b · CLAUDE.md

block 2 · 10 min · exercises/02b-claude-md.md

In this exercise we will write a CLAUDE.md with /init and cut it down to the lines that earn their place, while Claude builds the E2a feature in a second terminal. Project facts go in the repo's CLAUDE.md, your habits in ~/.claude/CLAUDE.md. This repo has no CLAUDE.md on purpose.

  1. /init
  2. Delete every line the repo would tell it anyway
    For each line in CLAUDE.md, delete it if the repo itself would tell you the same thing (package.json, README, folder names, tests). Keep it under 30 lines.
  3. "Interview me about how I like to work." Project facts go in CLAUDE.md, your habits in ~/.claude/CLAUDE.md
    Interview me about how I like to work, five questions at most. Put what is true of this repo into CLAUDE.md and what is true of me into ~/.claude/CLAUDE.md.
  4. Let it build SPEC.md while you prune. Does it follow the file? (Start it in a second terminal; it runs while you finish.)
    Implement SPEC.md. Plan first, then build. Run npm test before you report done.
Done whenCLAUDE.md is under 30 lines and contains at least one line that came from something that actually happened, and the feature works (npm test is green, or the page shows it).

  • Run /memory to see what auto memory kept.

E3 · Build your own skill

block 3 · 15 min · exercises/03-your-skill.md

In this exercise we will write a skill and run it twice: once to see what it got wrong, once more after fixing the skill rather than the prompt. A task you repeat at work, or adding a chart to your dashboard as the fallback. The instructor demos /check and the Stop hook from the toolkit; both are stretches here.

  1. Think of a task you do repeatedly. Fallback: add a chart to your dashboard
  2. /skill-creator, or write SKILL.md by hand: task, input, desired output
    Create a skill <name>. Given <input>, it <does the task> and finishes by <how it shows the result>. Description: when to use it, one sentence.
  3. Run it: /your-skill
  4. What did it get wrong? Fix the skill, not the prompt. Run it again
Done whenThe skill has run twice and the second run needed no correction from you.

  • The Stop hook from toolkit/hooks/stop-run-tests.json: break a test, ask Claude to finish, watch it refuse.
  • /skill-doctor if your CLI has it.

E4 · Two in parallel, one reviewer

block 4 · 20 min · exercises/04-two-in-parallel.md

In this exercise we will run two Claude sessions at once, each building a change in its own worktree, and review each PR from an HTML walkthrough instead of the diff. Two dashboard features, or issues #2 and #4 if you want acceptance lists that are already written. Those two change the same create handler on purpose, so the second merge either conflicts or needs a careful look.

  1. Pick two small things: issues #2 and #4 in the repo, or two dashboard features
  2. Two terminals, claude --worktree ex4-<n> in each: "implement it, run the tests, open a PR"
    Implement issue #<n> (or: <the feature>). Run the tests before you report done. Open a PR with gh when green. Touch nothing the task does not need.
  3. A third session: "review PR #n and write an HTML walkthrough I can read without the diff"
    Review PR #<n> against its acceptance list. Then write a single-file HTML walkthrough at reviews/pr-<n>.html: what changed and why, each acceptance line and how it was verified, the risky parts, your findings by severity. Code only where a reader needs it.
  4. Read the walkthrough, not the diff. Merge, or send it back
Done whenTwo PRs are open, you have read one walkthrough, and at least one PR is merged or sent back with findings.
Stretch, Compound, Stuck?, long form
  • toolkit/agents/reviewer.md as the reviewer, /code-review alongside it, pr-triage when there are more PRs than you have time for.
  • Issue #6 as a third worker: your E1 dashboard served at /stats.
  • WORKFLOW.md in eight lines.
  • Take over a worker from your phone with Remote Control.

Long form (exercises/04-long-form.md, 45 min): three issues, the reviewer agent, merges that collide, WORKFLOW.md. For after the day, or for a group that finished the short form early. The walkthroughs land in reviews/, which is gitignored.

Compound: the reviewer's top finding: which CLAUDE.md rule or which test would have prevented it?

Stop 5 · The app: linkr

A link shortener small enough to read in ten minutes

node:http, a JSON-file store, no runtime dependencies. Two pages, three API routes, a redirect. It is here to practise on, and some of its defects are on purpose.

npm run seed       # load data/*.csv into the store
npm run dev        # http://localhost:3000  (PORT env to change)
npm test           # vitest, 27 tests, under 5 s
npm run lint       # biome; 37 warnings are expected to start with
npm run typecheck  # tsc --noEmit; CI runs it too

Seed before dev. The server reads the store once at start. If you seed while it is running, the next write overwrites what you seeded; npm run seed says so.

The store is .data/store.json, gitignored, written atomically. LINKR_STORE points it somewhere else; the check script uses a throwaway one.

routewhat it does
POST /links{ "target_url": "https://…" } → 201 { slug, target_url, created_at }; a body over 64 KB gets 413. A bad URL is accepted today: issue #5.
GET /:slugRecords the click, 302 to the target; 404 when unknown. HEAD redirects without counting.
GET /api/linksEvery link as JSON, newest first; after seeding each carries owner and campaign_id.
GET /api/stats?since={ total_clicks, top_links, by_day, by_referrer }; since is YYYY-MM-DD or a UTC datetime, anything else is 400.
GET / · GET /linksCreate a link · list links. Every GET also answers HEAD; a wrong method on a known path is 405 with Allow; an unknown path under /api/ is a JSON 404.

Where things live

server.ts routes and startup · api/links.ts the three API handlers, and the file issues #2 and #4 both change · redirect.ts the click · store.ts the file · validate.ts slug and URL rules, where issue #5 lives · web/ the two pages.

Known to be wrong to start with

Issue #5: not a url returns 201, the one FAIL row /check shows. Issue #7: 37 Biome warnings; npm run lint passes, --error-on-warnings does not. Issue #8: app/README.md documents a --port flag, but only PORT is read.

Links can expire

Optional expires_at on create; after that, GET /:slug is 410 with a small page and records no click. The open question the E2a interview should reach: what happens to an expired link's stats?

A user-chosen slug on create: 3 to 32 characters, letters, digits, - and _; reserved words are 400; a taken slug is 409. /MyLink and /mylink resolve to the same target.

Stop 7 · The toolkit

Reference implementations you copy in when you want them

Claude Code only loads what sits under .claude/. cp -r toolkit/skills/check .claude/skills/ and the skill is live in your session within seconds; /skills shows what loaded.

shapewhat it iswhen it is the right onecost
SkillInstructions the agent follows when you run /name or when its description matches what you askedA repeatable procedure that needs judgementThe description is in context always; the body only when used
HookA command that always runs on an event; exit 2 blocks it with a message the agent readsA check that must not be skippableZero context
SubagentAn agent definition with its own clean context and tool list; returns a result, not a transcriptThe checker must not share the writer's context, or work you want to fan outIsolated; the result is summarised back

skills/

check
The app's full check: tests, lint, live endpoints, one page, as a PASS/FAIL table with evidence on every row. Two ADAPT: lines to change. Not Claude Code's built-in /verify, which drives the app and records its own recipe; this one prints the table the reviewer and the loop gate on.
run-app
Start the app on a free port, print the URL, stop it.
add-chart
Adds a chart to the dashboard in the pattern the file already uses. A finished version of the E3 fallback; write yours first.
dataset-profile
Profiles every CSV in a folder, including values whose shape differs from the majority. An E1 stretch.
handoff
Writes a handoff note. An example of a personal skill.
pr-walkthrough
A single-file HTML walkthrough of a PR, readable without the diff. The E4 move as a skill.
the loop skills
reflect, groom, groom-prep and pr-triage: the four skills that make a loop repeatable.

agents/

reviewer.md
Reviews a diff against the issue's acceptance list, runs the check script, exercises every line literally, returns findings by severity with file:line, never edits. Read-only by instruction; Bash stays for git and gh.
researcher.md
A read-only mapper for "where does X happen" questions. Read-only by construction: no Edit, Write or Bash.

hooks/

stop-run-tests
Stop: runs npm test; on red it exits 2 with "tests red, not done". Bounded to three blocks per session. The instructor's demo in block 3, and an E3 stretch.
post-edit-format
PostToolUse on Edit and Write: Biome formats the file. Never blocks.
notify-done
Stop: a macOS notification when a turn ends.
